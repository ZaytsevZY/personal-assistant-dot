# 项目内统一调度

## 单一配置来源

调度定义统一维护在项目的注册表中，不分别在聊天应用、系统定时器和云平台手工设置互不关联的任务。[调度样例](../config/schedules.example.json)定义每日新闻与每周开源检查两个稳定任务 ID，初始均不启用。具体时刻、时区、目标账号、地址和密钥留在仓库外的私有覆盖配置中。

本地 MVP 的 `/schedule` 仅查看注册表；`/run` 只手动运行独立的合成演示工作流，不触发每日新闻或每周真实开源任务。没有调度后端，不能通过编辑配置启用网络、投递或后台执行。

未来调度器读取“公共默认配置 + 私有覆盖”，形成一个经校验的有效配置，并展示版本、变更、下次执行时间、运行位置与投递能力。一个任务同一时刻只允许一个主执行后端；采用租约或锁防止本地与常在线实例双跑。修改频率从同一控制入口写回配置，不另建一份独立平台任务。

任务通过稳定的工作流 ID 交给可替换的执行 agent，不在调度项中写死 dot 会话、平台定时任务 ID 或专有命令。dot 更换为其他 agent 时保留原任务 ID、运行水位和投递去重状态，迁移步骤见[agent 可替换设计](agent-portability.md)。

## 默认与启用条件

默认每日新闻、每周开源检查并整理建议，不指定虚构的具体时间。启用前需要：时区、执行窗口、后端、运行预算、输出渠道能力、身份与目标确认、失败策略及一次端到端验证。重大新闻即时推送是独立可选能力，不能由每日任务的存在推定已启用。

## 运行位置

| 后端方案 | 优点 | 限制 |
| --- | --- | --- |
| 本地 Mac | 私人数据接近本地、部署轻 | 休眠、关机、断网时无法保证执行或送达 |
| 常在线自托管服务或设备 | 不依赖用户打开电脑，可向手机渠道投递 | 运维、凭据、网络安全和费用需配置 |
| 经验证的托管调度服务 | 可承担公开信息检索 | 必须确认执行环境与渠道支持；不能默认访问本地文件 |

GitHub public 仓库不是私人数据运行环境。即使未来选择 Actions，也不能将本地私人目录、提示词输入、账号映射或敏感日志放进公共构建产物。执行后端和公共代码托管是两个独立选择；本初稿不部署任一后端。

## 渠道与手机可达性

输入入口与输出渠道分别配置。用户可以在飞书或 dot 对话，但不能因此假定 dot 是任意外部程序可调用的推送接口。对 dot 先核实当前产品支持的接入、后台任务、主动投递与移动端通知能力；没有官方可用接口时，不通过非正式方式模拟推送。

飞书也需要确认具体账号、机器人或应用能力、目标会话、权限和手机通知。渠道配置使用逻辑引用，实际 ID 与凭据只在私人配置。输出渠道尚未决定，当前为空；只有验证了投递链路才显示“已启用”。

离线时保存待投递项及有效期，恢复后合并仍有意义的内容。重试使用幂等键、过期和次数上限；不要在用户不在电脑前时依赖桌面弹窗作为唯一渠道。发送成功、平台接受、用户实际收到分别记录，不能混为一谈。
