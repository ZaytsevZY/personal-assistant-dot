# 持续迭代与提交方案

## 默认节奏

每日关注新闻；每周检查开源项目并整理改进建议。频率可以调整。调度以项目中的单一注册表集中管理，见[调度设计](scheduling.md)，不在不同平台独立维护散落的任务。具体时刻、时区、投递渠道与重大新闻即时提醒尚未设置；本仓库没有运行中的定时器、GitHub Actions、后台进程或无人监督的公开提交。

生活与工作回顾可加入每周流程，月度质量检查可在积累样本后启用。电脑离线时的补跑与去重遵循[架构](architecture.md)。日常新闻原文、检索过程和个人输出不随频率自动提交。

## 每周改进循环

1. 收集：失败、明确反馈、使用负担、任务缺口与官方开源新进展，私人证据留在私人目录。
2. 评估：与当前方案比较，写出收益、风险、许可证、权限、成本、迁移和退出成本。没找到更好的方案就保持现状。
3. 提案：使用[变更模板](../templates/change-proposal.md)，区分私人配置和通用代码；公共案例从零合成。
4. 验证：使用合成数据进行小范围试验，测覆盖、准确性、失败恢复、时间与费用。不得把上游宣传当测试结果。
5. 审查与应用：用户选择策略或集成变更后才应用；为每次修改保留版本、依据与回滚方式。可逆的已授权实现工作不额外重复确认。
6. 仓库提交：整理一个目的明确的本地 diff，检查文件与元数据，运行公开检查，再按具体授权进行本地提交或可审查的 PR；首次发布也遵循相同检查。
7. 发布：GitHub 公开推送为独立操作，遵循[发布检查](privacy.md)。定期发现新项目不构成自动安装或自动公开的授权。

## 变更权限

| 变更 | 初始处理 |
| --- | --- |
| 搜索公开信息，形成候选列表 | 在已授权任务范围内开展 |
| 生成私人简报与改进草稿 | 留在已授权私人环境 |
| 调整兴趣、来源、频率、通知或模型 | 显示提案，遵循用户的范围与选择 |
| 新插件、权限、付费或模型数据外发 | 明确说明具体影响，获得对应授权 |
| 通用设计与代码 | 本地 diff、检查、人工审阅 |
| 公开提交与推送 | 无自动化；核对待发布内容和用户授权 |

## 版本与审计

dot 是最初的开发和控制宿主。未来更换 agent 时使用[接管模板](../templates/agent-handoff.md)，由新 agent 读取公共规则与已授权的私人状态，不依赖当前聊天会话。切换不自动改变输出渠道、频率或数据访问范围。

区分 `policy_version`、提示词版本、运行配置版本和代码提交。每次输出记载适用版本，不在公共 changelog 引用真实私人运行 ID。调整效果不好或用户撤回时恢复上个版本；数据结构有变化时保留迁移与恢复步骤。上游项目变化只触发研究，不能覆盖本地权限、用户控制或来源多样性规则。

模型权重训练与微调属于未来独立项目，需明确数据许可、目标、评估和删除机制，不能由推荐反馈自动启动。
